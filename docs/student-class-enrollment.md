# 학생 계정과 반 소속 구조

## 목적

학생 한 명이 같은 학원 안의 여러 반에 동시에 또는 순차적으로 소속될 수 있게 한다.
학생 계정은 개인에게 귀속하고, 수업·시험·숙제·출석·영상·클리닉 데이터는 학생이
선택한 반을 기준으로 조회한다. 카카오 로그인 작업과는 별도 브랜치에서 진행하며 이
구조가 먼저 `main`에 반영된 뒤 인증 브랜치가 이를 사용한다.

## 데이터 모델

- `students`: 학생 개인과 학원 귀속을 보관한다.
- `students.class_id`: 전환 기간 동안만 유지하는 호환용 대표 반이다. 신규 코드는 소속
  여부를 이 컬럼 하나로 판단하지 않는다.
- `student_class_enrollments`: 학생과 반의 소속 및 이력을 보관한다.
  - 상태: `SCHEDULED`, `ACTIVE`, `COMPLETED`, `WITHDRAWN`
  - `(student_id, class_id)`는 유일하다. 같은 반 재배정은 기존 소속 행을 활성화한다.
  - `started_at`, `ended_at`, `end_reason`, `created_by_teacher_id`, `version`을 보관한다.
- 첫 단계에서는 학생과 반이 반드시 같은 학원에 있어야 한다. 학원 간 이동은 지원하지
  않는다.

## 로그인 세션과 반 선택

학생 세션은 다음 값을 가진다.

- `userId`, `userRole=STUDENT`, `studentAcademyId`
- `activeStudentClassId`: 현재 조회·수정에 사용할 반
- `activeStudentClassReadOnly`: 종강 이력만 선택된 경우 변경 요청을 차단하는 값

`GET /api/auth/me`는 학생의 반 목록, 활성 반 ID, 조회 전용 여부를 반환한다.
`POST /api/auth/switch-class`는 요청 학생의 선택 가능한 소속인지 서버에서 검증한 뒤
세션 값을 변경한다. 화면은 전환 성공 후 새로고침하여 이전 반의 캐시와 컴포넌트 상태가
섞이지 않게 한다. 시험 응시 화면에서는 선택기를 숨긴다.

활성 소속이 하나 이상이면 `ACTIVE` 반만 선택할 수 있다. 활성 소속이 하나도 없으면 가장
최근 `COMPLETED` 반 하나를 조회 전용으로 연다. `SCHEDULED`와 `WITHDRAWN`은 선택할 수
없다.

## 현재 반이 적용되는 학생 기능

- 학생 기본 정보의 표시 반
- 수업 및 출석 통계
- 시험 제출 목록과 시험/결과 접근 권한
- 숙제 목록과 숙제 수정 권한
- 수업 영상과 시청 진도
- 클리닉 예정 정보와 최근 결과
- 일일 피드백 등 개별 리소스 접근 권한

교사 화면의 수업 출석 명단, 숙제 배정 명단, 시험 제출 명단, 영상 통계와 클리닉 명단도
`ACTIVE` 소속을 기준으로 생성한다. 마이그레이션 전 개발·테스트 데이터는 소속 행이 없을
때에만 `students.class_id`로 호환 조회한다.

## 교사 화면의 학생 반 관리

학생 목록에서 현재 소속 반을 표시하고 **반 관리**를 열어 소속과 종료 이력을 확인한다.
학생 기본 정보 수정은 이름·학년·학교를 수정하며, 반 변경은 아래 전용 기능을 사용한다.

- **반 추가**: 기존 반 소속을 유지하고 새 반을 `ACTIVE`로 추가한다. 종료했던 반을
  다시 추가하면 같은 소속 행을 재활성화한다. 이미 수강 중인 반은 중복 추가할 수 없다.
- **수강 종료**: 선택한 학생의 해당 반 소속만 `COMPLETED`로 바꾸고 `MANUAL_COMPLETION`
  사유를 남긴다. 반 전체를 종강하거나 학생의 학습 기록을 삭제하지 않는다.
- **반 이동**: 선택한 기존 소속을 `COMPLETED` / `TRANSFERRED`로 종료하고 대상 반을
  `ACTIVE`로 배정한다. 다른 반 소속은 유지한다. 두 변경은 한 트랜잭션으로 처리하며,
  대상 반 배정이 실패하면 기존 소속도 종료되지 않는다.

마지막 활성 소속을 종료한 학생은 완료된 반의 기록을 조회 전용으로 이용한다.
종강한 반에는 새로 배정할 수 없으며 먼저 반 운영을 재개해야 한다. 다른 학원의 반으로
배정할 수 없다. 같은 학생의 반 관리 요청은 학생 행 잠금으로 순차 처리한다.

| API | 동작 |
| --- | --- |
| `GET /api/students/{id}/enrollments` | 조회 가능한 소속과 종료 이력 |
| `POST /api/students/{id}/enrollments`, `{classId}` | 반 추가·재활성화 |
| `POST /api/students/{id}/enrollments/{classId}/complete` | 해당 소속 수강 종료 |
| `POST /api/students/{id}/enrollments/{classId}/transfer`, `{classId: 대상 반 ID}` | 해당 소속에서 다른 반으로 이동 |

변경 API는 변경 후 조회 가능한 소속 목록을 반환한다. `PUT /api/students/{id}`에서
기존과 다른 `classId`를 보내는 이전 반 변경 방식은 거부한다.

## 교사 권한과 반별 기록 격리

- 학원 관리자는 자신의 학원 전체 학생과 소속을 관리한다.
- 일반 선생님은 자신이 담당하거나 보조하는 반에 `ACTIVE` 또는 `COMPLETED` 소속이
  있는 학생을 조회한다. 소속 목록과 표시 반도 조회 가능한 반으로 제한한다.
- 반 추가는 학생과 대상 반의 권한, 수강 종료는 학생과 기존 반의 권한, 반 이동은
  학생·기존 반·대상 반의 권한을 모두 검사한다. 서로 다른 담당자 사이의 이동은
  양쪽 반에 권한이 있는 선생님 또는 학원 관리자가 처리한다.
- 조교는 배정된 반의 학생과 소속을 조회할 수 있지만 반 소속을 변경할 수 없다.
- 학생 개인 계정 삭제는 모든 반의 학습 기록에 영향을 주므로 학원 관리자만 가능하다.
  개별 반에서 수강을 마치는 경우에는 계정 삭제가 아니라 수강 종료를 사용한다.

학생을 조회할 수 있다고 그 학생의 다른 반 기록까지 볼 수 있는 것은 아니다.
시험·답안은 시험의 반, 숙제는 숙제의 반, 출석·영상 진도는 수업의 반,
클리닉 기록은 클리닉의 반을 기준으로 권한을 검사한다. 학생 상세의 수업·출석 통계도
선생님이 조회할 수 있는 소속 반의 범위에서 집계한다.

소속 행이 하나라도 존재하면 대표 반 컬럼으로 권한을 우회하지 않는다.
`students.class_id`는 아직 남아 있는 이전 코드의 호환 값으로만 유지한다.

## 반 종강과 재개

반을 종강하면 해당 반의 `ACTIVE` 소속은 `COMPLETED`로 바뀌며 종료 시각과
`CLASS_ENDED` 사유를 기록한다. 반을 잘못 종강하여 재개하면 이 사유로 완료된 소속만
다시 `ACTIVE`가 된다. 학생 소속 이력이 남아 있는 반은 삭제할 수 없고 종강 처리해야
한다.

## 배포 순서

1. DB 백업
2. `migrations/2026-08-29-01-add-student-class-enrollments.sql` 실행
3. 파일 마지막의 누락 소속 및 학원 불일치 검증 결과가 모두 `0`인지 확인
4. 애플리케이션 배포
5. 다중 소속 학생으로 반 전환 후 각 화면의 데이터 범위를 점검

운영 환경은 자동 마이그레이션을 쓰지 않으므로 테이블을 만들기 전에 코드를 배포하면
애플리케이션의 스키마 검증이 실패한다.

교사 반 관리·권한 전환 단계는 이미 적용한 소속 테이블과 컬럼을 사용하므로 **추가 DDL이
없다**. 배포 전 반 추가·이동·마지막 소속 종료와 서로 다른 담당 교사 사이의 권한을
검증한다. 이 단계에는 중복 계정 병합 및 카카오 로그인이 포함되지 않는다.
